# 从旧 Excel / Hermes 工作流迁移

本文用于把“Hermes、定时脚本或 openpyxl 直接修改旧 Excel”的工作流，安全切换到 Open Health Agent（OHA）的单一写入路径：

```text
微信 / Hermes / 手动命令 / ghealth
                 ↓
          OHA 共享锁与校验
                 ↓
        SQLite（唯一可写真源）
                 ↓
       Excel（原子生成的只读视图）
```

本仓库**目前不提供自动旧账本导入器**。下面是迁移设计和人工验收清单，不是可直接对真实数据运行的一键命令。任何暂停旧任务、读取旧工作簿、导入真实健康记录、替换工作簿、修改 OAuth 或安装后台任务的操作，都必须先得到用户针对该动作的明确确认。

## 迁移原则

- 先盘点和只读预演，再安排短暂停写窗口。
- 切换时必须停止所有旧 writer；只停定时任务而允许 Hermes 继续直接保存 Excel，仍会产生双写。
- SQLite 是迁移后的唯一可写真源；Excel 只由 OHA 从 SQLite 重建。
- 发现无法无损解释的字段、重复项或冲突时默认中止，不猜测、不覆盖。
- 旧工作簿、SQLite 和配置分别创建一致性备份；验证通过前不删除旧文件。
- 迁移工具必须把整批导入放在一个数据库事务中；任一校验失败则整批回滚。
- 健康账本与财务或其他私人账本分开，不把无关 sheet 复制进健康导出物。

## 1. 只读盘点与预演

先画出现有数据流，至少列出：

- 每个旧 Excel 文件及其中由脚本管理的健康 sheet；
- Hermes 会话中可能直接写 Excel 的工具、Skill 或提示词；
- cron、launchd、systemd、常驻进程和手动脚本等所有 writer；
- 每个数据源的时区、时间口径、稳定 ID、去重规则和最近写入方式；
- Google Health 使用的 profile、授权 scope 和网络代理要求；
- 旧工作簿是否混有财务、联系人、笔记等非健康内容。

预演只能读取元数据和必要字段，不写入旧文件或正式 SQLite。预演报告应包含：

- 各 sheet 的表头、可识别记录数和拟映射类型；
- 无法识别、字段缺失、时间无效和单位不明确的行数；
- 稳定 ID 冲突、内容相同但 ID 不同、ID 相同但内容不同的分类；
- 睡眠重叠、饮食与营养明细可能重复计算等专项警告；
- 预期新增、跳过、冲突和拒绝的数量，但不输出健康值或原始文本；
- 源文件哈希、文件大小和修改时间，供正式执行前做 TOCTOU 校验。

预演不等于授权正式导入。用户应看到迁移范围、冲突策略、停写时间和回滚方案后，再明确确认真实切换。

## 2. 定义字段映射

迁移实现应先把旧行转换为 OHA 的规范化候选记录，再写数据库。不要直接复制整行或把旧 Excel 当成新的数据库。

通用要求：

- 明确时区；无时区的本地时间只能按经用户确认的旧账本时区解释。
- 单位必须可证明；不从列名模糊猜测单位，也不静默换算未知量纲。
- 保留可审计的来源类型、旧记录标识和迁移批次，但不把文件系统路径或凭据写入公开字段。
- 对可重复投递的来源生成稳定 ID；不要仅用“时间 + 数值”合并本来可能是两次独立事件的记录。
- 空白、缺失、未同步或未佩戴不能转换为零。
- 旧表中的自由文本仅在确有必要且用户同意时迁移；建议默认最小化。

### 睡眠

- 按睡眠结束日归档，而不是简单按开始日或文件所在行日期。
- 区分 asleep、in-bed 和 awake；只有口径兼容时才推导实际睡眠时长。
- 同一晚来自设备总览、阶段明细和手工记录的区间可能重叠，不能直接相加。
- 无法判断来源优先级或重叠关系时标记冲突并中止，不选择看起来“更合理”的数值。

### 饮食与营养

- 只有明确已经摄入的食物才进入饮食记录；购买、计划或询问不能当作摄入。
- 一条餐食总览和它的营养明细可能代表同一事件，不能分别计入两次总量。
- 估算份量、营养范围、记录方式和置信度应保持可区分；不要把估算值提升为精确测量。
- 缺少关联键时，不要仅凭相近时间强行把食物行与营养行合并。

## 3. 取得确认并进入停写窗口

用户明确确认正式迁移后，按已盘点的清单暂停**所有**旧 writer：

1. 停止旧 cron、launchd、systemd 或常驻同步进程。
2. 禁止 Hermes 使用 `execute_code`、openpyxl、通用 terminal/file 工具直接保存旧健康 Excel。
3. 暂停人工编辑受管健康 sheet，并关闭可能自动保存的 Excel 会话。
4. 检查没有残留进程仍持有旧工作簿或准备写入。
5. 记录停写开始时间，之后到达的微信消息先排队，不让另一条路径落盘。

如果不能证明所有 writer 已停止，应取消迁移窗口。不要在“双写可能仍存在”的情况下继续。

## 4. 创建一致性备份

停写后再创建备份，确保源文件不会在复制过程中变化：

- 原样复制旧工作簿，并计算加密哈希；
- 使用 SQLite backup API 创建 OHA 数据库备份，不直接复制正在使用的 WAL 数据库文件；
- 备份私有配置、目标投影和必要的审计状态，但排除 token、媒体缓存和无关会话内容；
- 备份文件设为仅当前系统用户可读，并放在不会进入 Git 的私有位置；
- 记录备份哈希、时间、迁移版本和恢复顺序，不记录健康值或凭据。

若健康 sheet 与财务 sheet 位于同一个旧工作簿，备份仍应保留完整原文件用于回滚，但迁移输入只读取已确认的健康 sheet。新的健康工作簿不得包含财务或其他非健康 sheet。

## 5. 校验源快照，防止 TOCTOU

正式解析前重新读取源文件的哈希、大小和修改时间，并与预演报告比较：

- 任一属性变化：默认中止，重新预演并重新取得确认；
- 文件正在被占用或无法稳定读取：默认中止；
- 表头、sheet 集合或记录数变化：默认中止；
- 不能证明读取的就是用户确认过的快照：默认中止。

迁移过程中只读取这份已验证快照。不要在解析一半时重新打开可能变化的“最新”源文件。

## 6. 单事务导入与冲突处理

正式导入器应遵循以下事务边界：

1. 获取 OHA 唯一共享锁。
2. 打开现有 SQLite；数据库不存在时停止，不能隐式创建空真源。
3. 对源快照再做一次哈希校验。
4. 在内存或临时只读区域完成全部解析、规范化和交叉校验。
5. 开启一个数据库事务，写入全部记录、来源映射和迁移审计事件。
6. 运行数据库完整性检查和迁移后不变量检查。
7. 任一失败则回滚整个事务；全部通过才提交。
8. 提交后从 SQLite 原子导出新的独立健康工作簿。

冲突策略必须显式、可审计，默认规则如下：

| 情况 | 默认处理 |
|---|---|
| 稳定 ID 与内容都相同 | 幂等跳过 |
| 稳定 ID 相同但规范化内容不同 | 中止并要求人工决定 |
| 内容相似但来源 ID 不同 | 保留为独立候选，不自动合并 |
| 时间、单位、类型或来源无法解释 | 拒绝该批并中止 |
| 睡眠区间重叠且来源优先级未知 | 中止 |
| 饮食总览与营养明细关联不明 | 中止 |

不得提供“最后写入获胜”作为无人值守默认值。若用户决定如何处理某类冲突，应把规则限定到明确范围，并在新的预演报告中展示结果后再执行。

## 7. 导出与 `export_pending`

数据库事务提交和 Excel 导出是两个不同阶段：

- SQLite 提交成功、Excel 导出成功：迁移数据和可读视图都已更新。
- SQLite 提交成功、Excel 导出失败：不能把整次迁移报告为“未写入”。应返回 `export_pending` 语义，保留 SQLite 为真源，并从同一数据库重试导出。
- SQLite 事务失败或回滚：不得导出部分结果。

OHA 必须在任何可能持久化 SQLite 变化的操作之前先写入 workbook-projection outbox/pending 标记；数据库提交后，只有 Excel 原子替换成功才清除标记。这样即使进程在“SQLite 已提交、Excel 尚未完成”之间中断，`doctor`、`context` 和后续命令仍能发现并恢复投影，而不会把已成功的数据写入误报为失败或丢失。

若目标工作簿位于 iCloud、OneDrive、Dropbox 等已识别同步目录，正式含健康数据的投影前必须取得独立 `cloud-workbook` scope 同意。未授权时迁移/记录/同步仍可把 SQLite 写成功，但 Excel 保持不变且状态为 blocked/pending；授权后从同一 SQLite 运行 `open-health-agent export`。撤回 consent 不会删除云端已有副本，提供商侧同步或文件仍须另行停用/删除。

`cloud-workbook` 与 `cloud-private-home` 必须分开处理，并且都绑定具体 provider/path。新的私有 home 不应建在同步目录；旧安装若已经把私有 home 或 SQLite 放入 iCloud、OneDrive、Dropbox 等同步目录，正式切换前优先迁回本地。只有用户明确选择临时保留 legacy 布局时，才记录 `cloud-private-home`，且移动目录、数据库或更换同步提供商后旧授权失效。该授权不等于允许把 Excel 投影到云端，后者仍需 `cloud-workbook`。

出现 `export_pending` 时，禁止用旧 Excel 反向覆盖 SQLite，也禁止恢复旧 writer。先修复 consent、导出目标、权限、磁盘空间或文件占用，再重新从 SQLite 生成工作簿。

## 8. Google Health、代理和定时任务切换

只有在手动同步、导入和导出都验证通过后，才切换自动同步：

1. 为 OHA 使用独立、经确认的 `ghealth` profile。
2. 重新授权时只申请当前导入所需的最小 scope：活动与健身只读、健康测量只读、睡眠只读。
3. 不沿用覆盖营养、位置、profile、settings、ECG 或其他未使用数据的宽泛授权。
4. 旧 token 确认不再需要后，按提供商流程撤销；不要把 token 内容复制到迁移日志或聊天。
5. 确认首次说明已经成功送达，记录有效的 `google-health` scope 同意；若工作簿在同步目录，也先记录 `cloud-workbook` 同意。再以最终使用的系统用户、ghealth profile、账号、Cloud 项目、时区和 OHA runtime 完成一次真实手动同步，且结果必须同时是 `status=success` 与 `workbook_export=succeeded`；fixture 或云投影 blocked 的同步不能作为安装凭据。
6. 真实手动同步成功后 30 分钟内取得一份新的、一次性 `scheduler` scope 同意，并立即安装一个 OHA scheduler。安装尝试会消费这份同意；失败后重试也要重新取得同意。
7. scheduler 必须绑定 ghealth、Python、OHA 代码、profile、账号、项目、scope/认证方式和时区；成功安装后，还要把持续运行授权绑定到该手动同步的静态 runtime 与账号 runtime 指纹，并在健康查询前同时拒绝 consent、installed authorization 或指纹漂移。撤回先使本地授权失效，因此删除失败的孤儿任务不能复活；之后只重新 grant 也不能复活，必须完成新的合格同步与成功重装。
8. 若后台同步依赖代理，只通过 HTTP/HTTPS/ALL/NO_PROXY 白名单传递。代理文件必须归当前用户所有且仅本人可读，除这些键与注释/空行外不得包含其他内容；proxy URL 只能指向无凭据的本机回环地址并包含有效端口。
9. 如需 AC 供电时保持唤醒，另行取得 `keep-awake` scope 同意；它与 scheduler grant 都是一次性的，必须在授予后 30 分钟内用于一次安装尝试。scheduler 同意不包含保持唤醒。
10. Google 外部 fetch 采用两阶段锁：writer lock 内只固定本地授权、配置、日期和本地 runtime 快照；`ghealth` profile、账号、时区、指纹和网络读取都在锁外完成；随后先锁外复核外部身份，再短暂持锁验证本地快照完全相同才提交。停写窗口内仍应禁止旧 writer；若 fetch 期间 OHA consent、身份或配置变化，拒绝整批结果并重新预演/同步。

不要同时恢复旧定时脚本和安装 OHA scheduler。正式环境只能保留一个健康同步 writer；仓库安装器不会自动完成 scheduler 安装或旧任务切换。

## 9. 验证清单

切换前后都使用脱敏计数、哈希和状态验证，不在普通日志中打印健康值：

- SQLite `quick_check` 通过，schema 版本与 runtime 兼容；
- 迁移事务的输入、写入、跳过、拒绝和冲突数量可对账；
- 每种记录类型的日期覆盖与预演一致；
- 稳定 ID 唯一，重复运行同一快照不会增加记录；
- 睡眠没有被重叠来源相加，饮食与营养没有双计；
- 新 Excel 只包含健康视图和允许的说明页，不包含旧财务或其他私人 sheet；
- Excel 可打开，受管 sheet 由 SQLite 重建，数据库与导出状态一致；
- `doctor` 不报告数据库缺失、工作簿漂移、导出待处理或时区不一致；
- 手动小窗口同步成功，随后重复同步保持幂等；
- Hermes 新会话不能通过通用工具直接保存 Excel，也不把健康内容写入全局 memory；
- 其他消息渠道均限制为本人或关闭，不能借共享 profile 访问健康工具；
- scheduler 状态正常，且旧任务确实保持停用。

完成上述验证并得到用户确认后，才把新路径设为正式入口。旧工作簿应只读归档一段经用户同意的观察期，不立即删除。

## 10. 回滚

迁移前应先写下回滚触发条件，例如数据库校验失败、计数无法对账、工作簿导出持续失败或消息入口绕过 OHA。

回滚顺序：

1. 停止新 scheduler 和所有 OHA writer，保留故障现场的只读副本。
2. 若数据库事务未提交，确认已完整回滚；不要手工删除部分行。
3. 若事务已提交，使用迁移前 SQLite backup API 生成的备份恢复整个数据库，而不是逐行反向修改。
4. 恢复迁移前的私有配置和投影，运行完整性检查。
5. 仅在用户明确确认后，才临时恢复某一个旧 writer；不要一次恢复多个旧入口。
6. 对变化过的源重新盘点和预演，再安排下一次切换。

回滚不是删除审计证据。保留迁移批次、失败阶段、脱敏错误分类和备份哈希，直到用户确认新流程稳定并决定归档策略。

## 11. 完成标准

只有同时满足以下条件，迁移才算完成：

- 用户已明确确认真实迁移和最终切换；
- 所有健康写入都经过 OHA 的共享锁、校验和 SQLite；
- Excel 只是独立健康工作簿的原子导出视图；
- 旧直接 Excel writer 与旧定时任务保持停用；
- OAuth、代理、scheduler 和保持唤醒分别遵循最小权限与独立同意；
- 幂等、数据覆盖、专项映射、导出和回滚验证均通过；
- 旧混合工作簿已只读归档，未把财务或其他私人数据带入健康账本。

在自动导入器完成字段映射、干跑报告、哈希校验、单事务写入、冲突中止和测试覆盖之前，不应把本页转换成未经审计的临时脚本直接运行于真实数据。
